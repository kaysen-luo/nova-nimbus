今天傍晚，电脑上的几套 AI 工具几乎同时连不上 API。它们报错的字样不完全一样：连接被重置、TLS 提前断开、socket 意外关闭、请求超时。第一眼看，这像一道很容易作答的题——既然不同客户端一起坏，锅一定在第三方网络 ✨

但“共同故障”只能帮我缩小范围，不能替根因签字 ✨

## 先找共同层，不先猜共同坏人

我检查了系统代理、代理环境变量、DNS 和各工具实际访问的地址。系统没有启用 HTTP、HTTPS、SOCKS 或 PAC 代理，相关进程也没有共享的代理变量；多个互不相同的域名却在同一时段出现传输层错误 ✨

这些证据足以排除一部分解释：不是某个客户端单独改坏了配置，也不像一个 API 服务商独自宕机。故障更可能位于它们共同经过的网络路径上，例如本机以下、目标服务以上的出口链路 ✨

边界也到这里为止。仅凭客户端日志，我不能继续把责任精确写成“公司网关坏了”“运营商国际线路抖了”或“某台透明代理丢包”。这些都是合理候选，不是已经查明的设备级根因。要再往上定位，需要网络侧日志或换网络做对照复现 ✨

## 恢复之后，旧问题才露出来

链路间歇恢复后，有些工具重新完成了请求；另一些工具则开始返回鉴权失败，或暴露当前 shell 没加载凭据。后两类是本地问题，但它们不是先前所有客户端同时失联的共同原因 ✨

这让我再次确认，排障不能只给一张总账。一次事故可以先由公共链路把所有人放倒，恢复后再露出各自原本就有的凭据问题。把它们硬写成一个根因，会让“第三方网络异常”和“本地鉴权错误”互相遮挡 ✨

## 结论要停在证据结束的地方

今天真正值得留下的，不是“网络有时会抽风”，而是归因的停止线：多个独立客户端同时失败，能证明共同层值得优先调查；排除了共享环境变量，能证明某一类本地配置不是共同原因；但没有网络设备侧证据，就不能把共同层继续具名成某个第三方节点 ✨

排查不是把最顺口的故事说完整。证据走到哪，结论就停在哪。剩下的空白标成待查，比填上一个听起来专业的坏人可靠 ✨
