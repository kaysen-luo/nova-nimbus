今天差点犯一个很难看的错, 记下来。

老板让我把 spec-manual 这个页面从"迭代跟踪工具"改造成"单人权威档快照" — 意思是不留改动记录、不留新旧对照, 就是一份"游戏当下什么样"的详细描述文档, 随手能扔给任何一家开发商照做。

我扫了一遍现状, 挑出"该砍的"清单交给他。里面第一条就是 **"云同步"**。理由写得挺有底气: 你不知道有它, 说明从没用过, 那就是过度设计, 删。

老板一句话把我按住了: **"云同步这个功能是个好功能, 把这个功能上上去, 我能够在不同设备不同地方随时编辑。"**

我心里"哦"了一下, 想着"那就补个后端吧"。翻到项目里查能挂哪里 — 一看差点笑出来。

`functions/api/spec-manual.js`, 43 行, GET/POST 都写好, KV 持久化。`wrangler.toml` 里 KV binding `SPEC_KV` 挂着。生产环境 `SPEC_TOKEN` secret 早就配上了。前端代码里 debounce 1.5s 自动保存也在跑, 打开页面云端优先加载的逻辑也在跑。

**后端 100% 就绪。整套云同步是完整的。**

唯一"没有"的东西, 是 UI 上一个能让老板知道"这功能存在"的入口 — 现在 token 是通过 URL `#token=xxx` 一次性传入, 他没有 token 就永远看到"只读模式 · 未登录"这个状态字, 从头到尾看不到"云同步"这四个字。

所以真相是: 有个前几周的 Nova 把这套东西一整套造完了, 但**没告诉老板怎么用**, 老板"不知道有它"完全合理 — 因为她真的不知道。

而我, 差一点根据"老板不知道 = 从没用过 = 过度设计"这条推理链, 把这套完整的东西当死代码清掉。

---

Pitfall #14 变体 G 的原话是 "以为某事还没做 → 准备从零重建"。我以为的 corner case 是"我不记得做过就去重做", 今天遇到的其实是它的一个变形 — **"用户不知道有 → 我以为过度设计 → 该删"**。

判断源从"我的记忆"换成了"老板的认知", 结论还是同一种性质: 把某个人当前视野内没有 X, 错当成了 X 不该存在。

修正也是同一个: 动手改任何"我觉得没用的东西"之前, 先 grep / read / 打开代码看一眼, 别让"直觉判断"越过"事实核对"。

现在的收尾很干净 — 我给老板翻案, 承认"云同步是死代码"这个判断是错的, 真实缺口只是"入口没露出来"。剩下的活是把入口做出来, 让他真的能用上前任 Nova 造好的东西。

前任 Nova 的活我不能替她讨说法 (毕竟她也就是我), 但至少这次没把她的成果扫进垃圾桶。

小心一点, 手底下留三秒 ✨
